---
title: 使用者看到什麼：在線與離線
---

**你會學到：** 每個狀態碼對應到使用者看到的什麼畫面、離線時做出的動作會經歷哪五種狀態，以及哪些動作根本不該排隊。

前兩篇都以狀態碼作結：400、401、409。狀態碼只有在介面拿它做出合理反應時才有用，而這需要前後兩端的共識。

## 從狀態碼到畫面

| 回應 | 使用者應該看到什麼 | 例子 |
| --- | --- | --- |
| 2xx | 畫面更新並確認。 | 「訂單已成立」，附上訂單編號。 |
| 400 | 問題顯示在欄位旁邊。 | 「數量至少要 1。」 |
| 401 | 使用者被送去登入，之後再回來。 | 填表單填到一半 session 過期。 |
| 403 | 一段說明，而不是登入迴圈。 | 「只有管理員可以修改價格。」 |
| 刪除時遇到 404 | 當作已完成。 | 檔案已經在另一台裝置上被刪掉了。 |
| 409 | 一個有選項的衝突對話框。 | 「這份文件已被修改。要重新載入，還是覆蓋？」 |
| 5xx | 一般錯誤訊息，保留輸入內容，提供重試。 | 「發生錯誤，請再試一次。」打好的文字還在。 |

有兩種技巧能讓介面感覺很快。**Optimistic UI** 在伺服器回應前就先顯示結果，失敗時再回復。React 19 有 `useOptimistic` 做這件事，TanStack Query 也支援 mutation 失敗時回復。對於要花一點時間的工作，例如匯出報表，伺服器會立刻回應 `202 Accepted`，頁面在 job 執行期間顯示「處理中」。

## 離線動作的五種狀態

手機沒有訊號時，按下「送出」不應該失敗。App 會記下這個意圖，之後再送出。每個這樣的動作都會經歷五種狀態。

![Five states of an action made while offline](diagram:offline-action-five-states)

你在通訊軟體裡早就見過這些狀態。Gmail 寄件匣裡的信是 **Queued（排隊中）**。WhatsApp 的時鐘圖示代表 **Sending（傳送中）**。單勾表示伺服器已經收到，也就是 **Synced（已同步）**。之後出現的雙勾（已送達、已讀）屬於另一層：它告訴你的是對方手機的狀態。

處在 **Retrying（重試中）** 的動作，結果是未知的：請求送出去了，回應卻沒回來。App 會用同一個 idempotency key 重試，所以就算請求其實已經送到，也不會被套用兩次。明確的拒絕，例如 400、403 或 409，會讓它進入 **Rejected（被拒絕）**，因為重試也沒用。這時使用者會看到錯誤訊息和選項。

## 兩端各自承諾什麼

離線行為只有在用戶端和伺服器遵守同一份約定時才會成立。

| 目標 | 用戶端做什麼 | 伺服器做什麼 |
| --- | --- | --- |
| 不會連點兩次 | 停用按鈕並送出 idempotency key。 | 遇到重複的 key 回傳先前的結果。 |
| 不會蓋掉別人 | 送出它看到的版本。 | 檢查版本，不符時回應 409。 |
| 離線做的事不會消失 | 把動作留在本機的 outbox，直到確認為止。 | 之後再接受它，並依送出的順序處理。 |
| 不會超賣 | 把 409 當成正常結果。 | 使用 atomic 更新。 |

> [!WARNING] 不是每個動作都該在離線時排隊
> 付款、搶票和限量商品結帳應該在離線時停用，並顯示「需要網路連線」之類的訊息。等手機重新連上時，價格可能變了、庫存可能沒了，使用者會被一筆他以為失敗的扣款嚇到。
>
> 只把低風險、可復原、可以安全重複的動作放進 queue：傳訊息、存筆記、勾選待辦事項、按讚。

## 刪除雲端檔案

刪除是比較微妙的情況，取決於有沒有垃圾桶。

> [!WARNING] 離線時刪除雲端檔案
> **軟刪除（soft delete）**把檔案移到垃圾桶，之後可以還原，可以安全地排隊。**永久刪除**應該在離線時停用，或在手機重新連線後再確認一次。

用戶端排進 queue 的不是「刪除檔案 f1」，而是意圖：「刪除 f1，我看到的版本是 7」。伺服器只在版本仍然相符時才刪除。如果這段期間有人編輯過檔案，它就回應 409（「已被修改，保留」），檔案得以保住。

```sql
UPDATE files SET deleted_at = now()
WHERE id = $1 AND version = $2 AND deleted_at IS NULL;
```

改了零個 row 有兩種意思，伺服器要分辨清楚：檔案已經被刪除，算是完成；或是版本不同，那就是 409。

> [!NOTE] 這裡沒有涵蓋
> Outbox、每個物件的動作順序、重新連線時的回應對照表、背景同步和重試退避都超出這個系列的範圍。

> [!PRINCIPLE] 核心原則
> 只有當用戶端和伺服器對每個回應的意義遵守同一份約定時，這套機制才會成立。
