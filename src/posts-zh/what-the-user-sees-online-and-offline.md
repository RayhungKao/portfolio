---
title: 使用者看到什麼：連線與離線
---

**你會學到：** 每個狀態碼該讓使用者看到什麼畫面、離線時做的操作會經過哪五種狀態，以及哪些操作根本不該等連線後再送。

前兩篇最後都講到狀態碼：400、401、409。狀態碼要讓畫面做出合理的反應才有意義，這需要前端和後端事先講好。

## 從狀態碼到畫面

| 回應 | 使用者該看到什麼 | 例子 |
| --- | --- | --- |
| 2xx | 畫面更新，並告訴使用者成功了。 | 「訂單已成立」，附上訂單編號。 |
| 400 | 在出錯的欄位旁邊顯示問題。 | 「數量至少要 1。」 |
| 401 | 先帶使用者去登入，登入後再回到原本的地方。 | 表單填到一半，session 過期了。 |
| 403 | 一段說明，而不是一直被要求登入。 | 「只有管理員可以修改價格。」 |
| 刪除時遇到 404 | 當作已經刪掉了。 | 檔案已經在另一台裝置上刪除。 |
| 409 | 一個讓使用者選擇怎麼處理的對話框。 | 「這份文件已經被修改過。要重新載入，還是直接覆蓋？」 |
| 5xx | 一般的錯誤訊息，保留使用者輸入的內容，並讓他重試。 | 「發生錯誤，請再試一次。」打好的文字都還在。 |

有兩種技巧能讓畫面感覺更快。**Optimistic UI** 是在伺服器回應之前就先顯示結果，失敗了再改回來。React 19 的 `useOptimistic` 就是做這件事，TanStack Query 也支援 mutation 失敗時自動還原。至於比較花時間的工作，例如匯出報表，伺服器可以先回 `202 Accepted`，讓頁面在 job 跑的期間顯示「處理中」。

## 離線操作的五種狀態

手機沒有訊號時，按下「送出」不該直接失敗。App 應該先記下使用者想做的事，等有網路再送出去。每一個這樣的操作，都會經過五種狀態。

![Five states of an action made while offline](diagram:offline-action-five-states)

這些狀態你在通訊軟體裡早就看過。Gmail 寄件匣裡還沒寄出的信，就是 **Queued（排隊中）**。WhatsApp 訊息旁的時鐘圖示代表 **Sending（傳送中）**。出現一個勾，表示伺服器收到了，也就是 **Synced（已同步）**。之後的兩個勾（已送達、已讀）是另一回事：那是在告訴你對方手機的狀態。

在 **Retrying（重試中）** 的操作，結果是不確定的：請求送出去了，但回應沒有回來。App 重試時會帶同一個 idempotency key，所以就算第一次其實已經送到，也不會被執行兩次。如果收到明確的拒絕，例如 400、403 或 409，就會進入 **Rejected（被拒絕）**，因為再試也一樣。這時要讓使用者看到錯誤訊息和可以選的處理方式。

## 前端和後端各自要做到什麼

離線功能要能正常運作，client 和伺服器必須遵守同一套約定。

| 目標 | client 要做的 | 伺服器要做的 |
| --- | --- | --- |
| 連按兩下不會執行兩次 | 按下後停用按鈕，並送出 idempotency key。 | 遇到重複的 key，回傳上一次的結果。 |
| 不會蓋掉別人的修改 | 送出它看到的版本號碼。 | 檢查版本，對不上就回 409。 |
| 離線時做的事不會不見 | 把操作存在本機的 outbox，直到伺服器確認收到。 | 晚一點收到也照樣接受，並依送出的順序處理。 |
| 不會超賣 | 把 409 當成正常的結果處理。 | 用 atomic 的方式更新。 |

> [!WARNING] 不是每個操作都該等連線後再送
> 付款、搶票、限量商品結帳，在離線時都應該停用，並顯示「需要網路連線」之類的訊息。等手機重新連上時，價格可能變了、庫存可能沒了，使用者還會被一筆他以為沒成功的扣款嚇到。
>
> 只有風險低、可以還原、重複做也沒關係的操作，才放進 queue：傳訊息、存筆記、勾選待辦事項、按讚。

## 刪除雲端上的檔案

刪除比較複雜一點，要看有沒有垃圾桶。

> [!WARNING] 離線時刪除雲端檔案
> **Soft delete** 只是把檔案移到垃圾桶，之後還能還原，所以可以先排隊、等有網路再送。**永久刪除**在離線時應該停用，或等手機重新連線後再請使用者確認一次。

client 放進 queue 的不是「刪除檔案 f1」，而是完整的意圖：「刪除 f1，我看到的是第 7 版」。伺服器只有在版本還對得上時才刪除。如果這段期間有人改過這個檔案，就回 409（「檔案已被修改，保留不刪」），檔案就不會被誤刪。

```sql
UPDATE files SET deleted_at = now()
WHERE id = $1 AND version = $2 AND deleted_at IS NULL;
```

改到零個 row 可能有兩種原因，伺服器要分清楚：檔案早就刪掉了，那就算完成；或是版本不同，那就回 409。

> [!NOTE] 這篇沒有講到的
> Outbox 的實作、同一個物件上多個操作的順序、重新連線時每種回應該怎麼處理、背景同步，以及重試的間隔怎麼拉長，都不在這個系列的範圍內。

> [!PRINCIPLE] 核心原則
> client 和伺服器對每一種回應的意思有共識，這整套機制才能運作。
