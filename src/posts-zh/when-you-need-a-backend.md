---
title: 什麼時候需要後端
---

**你會學到：** 怎麼判斷一個網站需不需要後端，以及一個完整的網路服務由哪些部分組成。

很多網站其實不需要後端。作品集、部落格、文件網站，本質上就是一堆檔案，而 CDN 本來就能直接提供檔案。但只要訪客可以登入、付款、留言或上傳，情況就不一樣了。下面五個條件可以幫你判斷：只要有任何一個成立，就需要後端。

## 五個條件

| 條件 | 意思 | 例子 |
| --- | --- | --- |
| 機密 | 程式要用到一把絕不能出現在瀏覽器裡的金鑰。 | 用 Stripe 刷卡。Secret key 可以退款、讀取客戶資料，所以只能放在你的伺服器上。 |
| 共享、而且要保存下來的資料 | 資料在分頁關掉後還要在，而且不只一個人看得到。 | 文章的留言和按讚。`localStorage` 只存在某台裝置的某個瀏覽器裡，存在那裡的讚別人看不到，使用者換一支手機也就沒了。 |
| 可信的判斷 | 就算使用者想作弊，也必須守住的規則。 | 價格、庫存和權限。伺服器會自己重算購物車總額，瀏覽器上的數字只是拿來顯示。任何人都能改自己瀏覽器裡跑的 JavaScript。 |
| 不靠瀏覽器的工作 | 不管分頁有沒有開著，都必須完成的事。 | 結帳後的確認信、每晚的銷售報表、上傳影片後的轉檔。 |
| 瀏覽器連不到的系統 | 沒有開放到網際網路上，或根本不走 HTTP 的資源。 | PostgreSQL 資料庫在防火牆後面，用自己的協定溝通。公司內部的 ERP 只接受公司網路的連線。 |

五個都不成立，就不需要後端。像這個作品集，是一個匯出成靜態檔案、放在 GitHub Pages 上的 Next.js 專案，五個條件一個都沒有。頁面只在建置時產生一次，之後就是一般的檔案。GitHub Pages 只會回傳已經存在的檔案，所以就算專案裡寫了 Route Handler，放在那裡也不會有任何請求進得來。

這五個條件要一個功能一個功能地看，不是整個網站一起看。一間商店的商品頁可以只是檔案，結帳卻需要後端；而有了這個後端之後，其他需要它的功能也都能用。

## 需要後端，不代表要自己架伺服器

這五個條件講的是「需要什麼能力」，不是「需要哪台機器」。託管服務也能提供這些能力。Supabase 或 Firebase 提供共享的資料庫、登入功能，以及在它們那邊執行的存取規則。Serverless function 可以保管你的機密、執行你的程式，而你不用管任何一台機器。

要自己架伺服器、租用平台，還是用 backend-as-a-service，是另一個決定，這個系列在挑技術棧時會再談。現在只要先想清楚：你需要哪些能力。

## 一個完整的網路服務長什麼樣子

把這五個條件套到一間線上商店，會得到六個方塊。

![Anatomy of a web service](diagram:web-service-architecture)

這個系列的每張圖，顏色的意思都一樣：紫色是你寫的程式，青綠色是你保存的資料，灰色是你的程式以外的東西。

| 方塊 | 做什麼 | 在線上商店裡 |
| --- | --- | --- |
| Client | 執行你發布出去、但已經不在你掌控中的程式。 | 筆電上的瀏覽器、iOS App。 |
| Edge | 位在你的伺服器前面，負責提供快取的檔案、處理 TLS、擋掉攻擊。 | Cloudflare 快取商品圖片，並擋掉惡意流量。每個人看到都一樣、由伺服器產生的商品列表，也可以快取在這裡。購物車因人而異，就不行。 |
| Backend | 你的程式。保管機密、執行規則。 | 一個 Node 服務，用 Next.js 的 Route Handler 檢查登入、計算購物車金額，再向 Stripe 扣款。 |
| Data store | 你保存的所有資料。 | PostgreSQL 存訂單和使用者，Redis 存 session，S3 存商品照片。 |
| Queue 和 worker | 回應請求之後才做的工作。 | 在 BullMQ 或 SQS 這類 queue 裡放一個「寄確認信」的 job，再由 worker process 拿去處理。 |
| 第三方服務 | 你會呼叫，但不是你在維運的系統。 | Stripe 處理付款，SendGrid 寄信。 |

Queue 和 worker 另外有一篇專門介紹：[Queues and workers](/blog/queues-and-workers)。現在只要知道它們的位置就好。

## 跟著一個請求走一遍

顧客按下「下單」之後，會依序發生這些事。大部分步驟背後，都是那五個條件之一。

1. 瀏覽器帶著購物車內容送出 `POST /api/orders`。
2. Edge 直接放行，因為它不快取 POST。
3. 後端確認是誰登入，從 PostgreSQL 讀出實際價格，重新計算總額。這是可信的判斷。
4. 後端用 secret key 呼叫 Stripe。這是不會離開伺服器的機密。
5. 後端把訂單寫進 PostgreSQL，再把一個「寄確認信」的 job 放進 queue。這是共享的資料，存在每台裝置都讀得到的地方。
6. 後端回傳 `201 Created`，瀏覽器顯示「謝謝您」。
7. 稍後，worker 拿到 job，請 SendGrid 把信寄出去。這是不靠瀏覽器的工作：這時顧客可能早就把分頁關了。

少了後端，這些重要的步驟就沒有地方執行：價格可以被竄改，Stripe 金鑰會出現在網頁原始碼裡，訂單只存在一個瀏覽器裡，確認信也永遠寄不出去。

> [!PRINCIPLE] 核心原則
> 需要後端只有一個原因：有些事瀏覽器做不到，或者不能交給它做。
