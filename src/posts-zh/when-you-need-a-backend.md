---
title: 什麼時候需要後端
---

**你會學到：** 怎麼判斷一個網站需不需要後端，以及一個完整的網路服務由哪些元件組成。

很多網站根本不需要後端。作品集、部落格或文件網站就是一資料夾的檔案，而 CDN 就能直接提供一資料夾的檔案。一旦訪客可以登入、付款、留言或上傳，情況就變了。有五個條件可以告訴你那一刻是否已經到來：只要其中任何一個成立，你就需要後端。

## 五個條件

| 條件 | 意思 | 例子 |
| --- | --- | --- |
| 機密 | 程式需要一把絕不能傳到瀏覽器的金鑰。 | 用 Stripe 刷卡。Secret key 可以退款、讀取客戶資料，所以只有你的伺服器能持有它。 |
| 共享且持久的狀態 | 資料要活得比一個分頁久，而且不只一個人看得到。 | 文章的留言和按讚。`localStorage` 只屬於一台裝置上的一個瀏覽器，存在那裡的讚別人看不到，使用者換手機也就不見了。 |
| 可信的決策 | 即使使用者心懷惡意也必須成立的規則。 | 價格、庫存和權限。伺服器會重新計算購物車總額，瀏覽器上的數字只是顯示用。任何人都能修改自己瀏覽器裡跑的 JavaScript。 |
| 不依賴瀏覽器的工作 | 不管分頁開著還是關了都必須發生的事。 | 結帳後的確認信、每晚的銷售報表、轉檔上傳的影片。 |
| 瀏覽器碰不到的系統 | 沒有對網際網路開放，或不講 HTTP 的資源。 | PostgreSQL 資料庫躲在防火牆後面，用自己的協定溝通。公司內部的 ERP 只回應公司網路。 |

如果五個都不成立，就不需要後端。像這個作品集這樣的網站——一個匯出成靜態檔案、放在 GitHub Pages 上的 Next.js 專案——一個條件都不需要。頁面只建置一次，之後以檔案形式提供。GitHub Pages 只會提供已經存在的檔案，所以專案裡就算寫了 Route Handler，在那裡也永遠不會回應任何請求。

這五個問題要一個功能一個功能地問，而不是一整個網站一起問。一間商店的商品頁可以是純檔案，結帳卻需要後端；而那一個後端之後就能服務所有需要它的功能。

## 需要後端，不等於要自己跑伺服器

這五個條件描述的是能力，不是機器。託管服務也能提供這些能力。Supabase 或 Firebase 給你共享資料庫、登入系統，以及在它們那一端強制執行的規則。Serverless function 能保管你的機密並執行你的程式，而你不需要照顧任何一台機器。

要自己跑伺服器、租平台，還是用 backend-as-a-service，是另一個獨立的決定；這個系列在挑選技術棧時會再回來談。現在要問的只是：你需要哪一種能力。

## 一個完整的網路服務長什麼樣子

把這五個條件放進一間線上商店，你會得到六個方塊。

![Anatomy of a web service](diagram:web-service-architecture)

在這個系列的每張圖裡，顏色代表的意思都一樣：紫色是你寫的程式，青綠色是你保存的資料，灰色是你自己程式以外的任何東西。

| 方塊 | 它的工作 | 在線上商店裡 |
| --- | --- | --- |
| Client（用戶端） | 執行你發佈出去、但你控制不了的程式。 | 筆電上的瀏覽器、iOS App。 |
| Edge（邊緣層） | 位在你的伺服器前面。提供快取檔案、終結 TLS、過濾攻擊。 | Cloudflare 快取商品圖片並擋掉濫用流量。一份對所有人看起來都一樣、由伺服器渲染的商品列表也可以在那裡快取。購物車是個人的，就不行。 |
| Backend（後端） | 你的程式。它持有機密並執行規則。 | 一個 Node 服務，用 Next.js Route Handler 檢查登入、計算購物車價格並向 Stripe 扣款。 |
| Data stores（資料儲存） | 你保存的一切。 | PostgreSQL 存訂單和使用者，Redis 存 session，S3 存商品照片。 |
| Queue 與 worker | 在請求已經回應之後才做的工作。 | BullMQ 或 SQS 這類 queue 存放一個「寄送確認信」的 job，由 worker process 拿去處理。 |
| 第三方服務 | 你會呼叫、但不是你在跑的系統。 | Stripe 處理付款，SendGrid 寄信。 |

Queue 和 worker 會有一整篇專文：[Queues and workers](/blog/queues-and-workers)。現在只要知道它們在哪裡就夠了。

## 跟著一個請求走一遍

當顧客按下「下單」時，會發生以下的事。大部分步驟都是五個條件之一在發揮作用。

1. 瀏覽器帶著購物車內容送出 `POST /api/orders`。
2. Edge 直接放行，因為它不會快取 POST。
3. 後端確認誰登入了，從 PostgreSQL 讀出真實價格並重新計算總額。這是可信的決策。
4. 它用 secret key 呼叫 Stripe。這是永遠不離開伺服器的機密。
5. 它把訂單寫進 PostgreSQL，並把一個「寄送確認信」的 job 放進 queue。這是共享狀態，存在每台裝置都讀得到的地方。
6. 它回傳 `201 Created`，瀏覽器顯示「謝謝您」。
7. 片刻之後，worker 拿到 job，請 SendGrid 寄出信件。這是不依賴瀏覽器的工作：顧客這時可能早就關掉分頁了。

把後端拿掉，重要的步驟就沒有地方可以執行：價格可以被竄改，Stripe 金鑰會躺在網頁原始碼裡，訂單只存在一個瀏覽器中，確認信也永遠不會寄出。

> [!PRINCIPLE] 核心原則
> 後端存在只有一個理由：有些事瀏覽器做不到，或者不能信任它去做。
